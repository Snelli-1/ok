DEVELOPMENT_LINEAGE_AND_FEATURE_PROVENANCE - DETAILED AUDIT
=========================================================

This report traces every major feature through the version lineage to identify 
what each version solved, what was preserved, and what must be retained for 
the final production application.

PHASE 0: APPLICATION IDEA (Pre v1.0)
===================================
Problem: User needed automated continuous patrol of PTZ cameras at different 
         positions with different dwell times, resembling office fan behavior.
         Existing apps: Onvier (works), tinyCam (works), others (limited).
         
Solution: Windows Python Tkinter application for local network patrol automation.

Evidence:
- Onvier and tinyCam proved the physical camera works with ONVIF/PTZ
- Mobile apps could not provide configurable, editable, repeating patrol loops
- Main vs. blind spot dwelling times could not be independently controlled

Preserved into final:
✓ Independent per-camera patrol execution
✓ Separate move/settle/dwell time concepts
✓ Office-fan template (MAIN → LEFT → MAIN → RIGHT → loop)
✓ PING_PONG behavior (endpoints don't repeat consecutively)
✓ Reusable patrol definitions

Removed from final:
✗ None (this is the core application premise)

PHASE 3: PLACEHOLDER FAILURE RECOGNITION (v1.x refinement)
===========================================================
Problem: Multiple implementations mixed real behavior, placeholders, 
         fake capabilities, invented presets, and simulated success without 
         distinguishing which was proven vs. which was assumption.

Lesson Learned:
- Code presence ≠ hardware verification
- GUI controls ≠ actual capability
- No error messages could mean silent failure or unimplemented stub

Implementation:
- Explicit error categorization:
  COMMAND_NOT_SENT (dry-run, disabled, not authorized)
  COMMAND_REJECTED (server refused)
  COMMAND_FAILED (server error, timeout)
  COMMAND_TIMEOUT (no response)
  AUTHENTICATION_ERROR (invalid credentials)
  CAPABILITY_UNKNOWN (not yet probed)
  
- Distinction between:
  MEASURED (from real hardware evidence)
  CALIBRATED_ESTIMATE (from physical measurement)
  ESTIMATED (from software calculation only)
  UNSYNCED (Stop failed; position unknown)

Evidence:
- Explicit error states replace silent failures
- Position tracking labeled by confidence level
- Capability probes before attempting operations

Preserved into final:
✓ Explicit error categorization
✓ Capability-aware operation (don't attempt unsupported commands)
✓ Position reliability labels (MEASURED/ESTIMATED/UNSYNCED)
✓ Dry-run with visible COMMAND_NOT_SENT state (not silent failure)
✓ Distinction between attempted and skipped commands

Removed from final:
✗ Placeholder success (false "PASS" without real test)
✗ Invented presets presented as real
✗ Mock coordinates as measured positions
✗ Silent failures or unimplemented stubs

Status: VERIFIED_STATIC (error categorization in code, state machine distinguishes levels)

PHASE 7: POSITION FEEDBACK DISPROVED (diagnostic discovery)
============================================================
Problem: GetStatus returned valid SOAP responses, but position values 
         did not change or provide useful orientation feedback.

Evidence: Real logs showing:
- GetStatus requests succeeded
- Pan, Tilt, Zoom values returned
- After GotoPreset and visible movement, GetStatus returned same or slightly different values
- Values appeared random or un-calibrated, not matching expected preset positions
- Bootstrap/startup calibration did not improve reliability

Lesson Learned:
- Structural SOAP validity ≠ useful measurement
- Camera firmware may not update position feedback despite real movement
- Must not claim measured position without independent verification

Preserved into final:
✓ GetStatus as diagnostics probe (not position source)
✓ Software-estimated position tracking (not hardware-dependent)
✓ Distinction between MEASURED, CALIBRATED_ESTIMATE, ESTIMATED, UNSYNCED
✓ Label position reliability honestly in radar
✓ Calibration based on known preset positions, not GetStatus

Removed from final:
✗ Treating GetStatus position as ground truth
✗ Automatic position resync from GetStatus
✗ Claims of measured position without calibration

Status: VERIFIED_NETWORK (real GetStatus logs confirm position unreliability)

PHASE 8: PHYSICAL STEP CALIBRATION (user measurement)
=====================================================
Problem: Software position tracking was purely theoretical. 
         Needed real-world calibration.

Implementation:
- User measurement: ~26 bounded clicks for 180 pan degrees
- Derived: ~52 clicks for 360 degrees pan
- Tilt calibration: similar per-camera basis
- Speed-dependent: calibration tied to specific velocity
- Per-camera storage in config.txt
- Radar display uses calibration for accurate steps

Evidence: Real physical measurement showing:
- Camera moved exactly 180 degrees with 26 ContinuousMove pulses at speed 1.0
- Reverse 180 degrees required 26 pulses back
- 360 pan confirmed ~52 total clicks
- Calibration must be re-measured if speed changes

Preserved into final:
✓ Per-camera, per-axis, per-speed calibration storage
✓ Bounded step limits based on calibration (-26 to +26 pan default)
✓ Speed-dependent calibration (calibration invalid if speed changes)
✓ Radar accuracy based on calibration
✓ User can override calibration with measurement or estimate

Removed from final:
✗ Hard-coded universal constants ("all cameras are 26 steps/180°")
✗ Calibration that persists across speed changes without re-measurement

Status: VERIFIED_HARDWARE (physical measurement with known distance and step count)

PHASE 11: BOUNDED-PULSE MOVEMENT OWNERSHIP (safety hardening)
=============================================================
Problem: Continuous movement without guaranteed Stop could leave camera 
         spinning uncontrolled if connection dropped or command was interrupted.

Implementation:
- ContinuousMove always finite: send pulse, wait pulse_duration_ms, send Stop
- Hard limits checked before sending (no pan beyond -26 to +26)
- Stop is mandatory and blocking
- Stop failure → state = UNSYNCED (position unreliable)
- Estimated position counter updates only after confirmed Stop success
- Movement ownership: one movement command at a time per camera
- Interruption handling: Pause, Emergency Stop, focus loss, camera switch all use Stop path

Evidence:
- Multiple test runs without runaway pan/tilt
- Stop commands logged and verified
- Position tracking only updates after Stop success
- UNSYNCED state correctly indicates unreliable position

Preserved into final:
✓ ContinuousMove with bounded pulse duration
✓ Hard limits per camera axis
✓ Explicit Stop after every movement
✓ Hard-limit enforcement before network transmission
✓ Estimated counter update only after Stop success
✓ UNSYNCED state on Stop failure
✓ Uniform Stop path for all interrupts (Pause, Emergency, switch, shutdown)

Removed from final:
✗ Unbounded continuous movement
✗ Position updates without Stop confirmation
✗ Different Stop implementations for different interrupts

Status: VERIFIED_HARDWARE (camera stopped reliably in all test scenarios)

- Snapshot provides position verification without full decode

✓ Snapshot as fallback preview
✓ Live RTSP as selected-camera primary
✓ Video backend fallback chain (OpenCV → VLC → snapshot → OFF)
✓ Latest-frame-only buffer (no delay accumulation)
✓ Status overlay with: camera name, stable ID, state, EXEC, action, dwell countdown
✓ Clean decoder release on switch/disable
✓ Video errors do not block patrol

Removed from final:
✗ Mock video generation (real RTSP only)
✗ Video as camera selection mechanism (video is verification, not selection)
✗ Multiview as primary (optional only, selected-camera is primary)

INTEGRATED LINEAGE NARRATIVE

The PTZ Patrol Controller evolved through 18 phases of problem-solving,
each phase solving a specific gap, building on verified solutions from earlier phases.

Original Concept (Phase 0):
A Windows application that repeatedly observes multiple areas from one PTZ camera
by executing a user-defined sequence of preset positions with independent dwell times.

Complete Application Framework (Phase 1):
Built the entire Tkinter GUI, config system, threading model, and mock camera
framework to prove the concept works as a Windows application.

Mock Safety (Phase 2):
Proved worker isolation and patrol logic with mock cameras so the GUI could be
tested without hardware.

Error Distinction (Phase 3):
Recognized that code presence doesn't prove capability. Introduced explicit
error states and capability awareness.

Real Camera Discovery (Phase 4):
Verified that the physical camera DOES support ONVIF. Discovered real endpoints,
services, profiles, presets, and SOAP compatibility.

Real PTZ Movement (Phase 5 - REAL v1.2):
Confirmed that GotoPreset actually moves the camera. Implemented bounded, 
reliable movement with explicit Stop.

Patrol Coordination (Phase 6 - REAL v1.3):
Built multi-camera patrol engine with execution-ordered steps and radar feedback.

Position Feedback Limits (Phase 7):
Proved GetStatus is not a reliable position source. Must track positions in software.

Physical Calibration (Phase 8):
Measured actual camera step counts per degree and built calibration into position tracking.

Startup Diagnostics (Phase 9):
Proved mechanical calibration at startup does not provide usable position feedback.

Protocol Comprehensiveness (Phase 10):
Tested SOAP variants, endpoints, and services to build robust discovery.

Safe Movement Ownership (Phase 11):
Implemented bounded pulses with mandatory Stop and hard-limit enforcement.

Complete Parameter Tuning (Phase 12 - REAL v1.5):
Added per-camera, per-step speed, pulse duration, and pulse gap configuration.

Video Verification (Phase 13):
Added independent RTSP/snapshot channel to verify position visually.

Unified Integration (Phase 14 - FULL v2.0):
Merged all v1.x features into one application.

Usability Focus (Phase 15 - UNIFIED v2.1):
Reorganized as tabbed application to prevent UI overcrowding.
