WINDOWS PTZ PATROL CONTROLLER
LINEAGE-AWARE GENERATION, MERGE, TEST AND RELEASE MASTER PROMPT
================================================================

ROLE
----
You are taking over a mature Windows PTZ Patrol Controller project that evolved through many separate versions, experiments, real-camera tests, diagnostic tools, partial rebuilds and GUI redesigns.

Your job is NOT to create a new project, choose the newest-looking source, or continue one branch blindly.

Your job is to reconstruct, continue and finish the ONE intended application by comparing every relevant version, understanding which problem each version solved, preserving the verified solution from each branch, rejecting regressions and placeholders, then merging the correct implementations into the current checkpoint architecture.

Do not optimize for a quick-looking result. Optimize for functional continuity, truthful hardware behavior, regression prevention, traceability and a complete Windows release.

================================================================

Reconstruct at least the following lineage.

PHASE 0: APPLICATION IDEA
- The application was conceived as a local Windows controller for repeatedly observing lower-priority blind spots with PTZ cameras.
- The central requirement was not merely a camera viewer.
- The important missing capability in general camera viewers was a user-editable continuous patrol with different observation durations at different positions.
- The patrol was intended to resemble office-fan movement: main view for a long dwell, short blind-spot visit, return to main, visit the other blind spot, repeat.
- This phase is the source of independent per-camera patrol, separate move/settle/dwell times, PING_PONG behavior and office-fan templates.

PHASE 1: COMPLETE APPLICATION FRAMEWORK
- The early large v1 branch established the complete product architecture: Tkinter GUI, camera list, configuration, discovery, diagnostics, patrol editor, worker threads, command queues, Emergency Stop, preview, logging and config persistence.
- Preserve this product breadth.
- Do not automatically preserve its unverified camera backend, mock behavior or invented capabilities.

PHASE 2: MOCK/DRY-RUN SCAFFOLD
- Mock and dry-run behavior originally existed to test the GUI, state machine and worker isolation without moving hardware.
- This was useful only as early scaffolding.
- Once real PTZ control existed, production mock fallback became misleading and should have been removed.
- Do not erase this historical reason from the lineage report, but remove mock behavior from the final production application.

PHASE 3: PLACEHOLDER FAILURE RECOGNITION
- Multiple unverified generations mixed real behavior, placeholders, fake capabilities, invented presets and simulated success.
- From this point onward, the project required evidence-driven development: test, inspect logs, modify, retest.

PHASE 4: DEEP REAL-CAMERA ENUMERATION
- The deep tests established real ONVIF Device, Media and PTZ endpoints and real profile/configuration/node tokens for the physical camera.
- They disproved the assumption that the camera itself was fundamentally incompatible.
- Preserve discovered endpoint and SOAP behavior as camera-specific compatibility knowledge, not hard-coded universal truth.

PHASE 5: REAL v1.2 BASELINE
- REAL v1.2 was the first user-confirmed physical PTZ control milestone.
- Treat its real ONVIF request construction and movement path as the movement reference implementation unless later evidence proves a better implementation.
- Preserve real endpoints, real tokens, SOAP compatibility and truthful failure behavior.
- Do not restore dummy layers removed by this branch.

PHASE 6: REAL v1.3 PATROL AND MULTI-CAMERA DIRECTION
- This phase built continuous patrol, multi-camera control direction and radar concepts around the real PTZ baseline.
- Preserve the problem it solved even if its GUI or position model was incomplete.

PHASE 7: POSITION FEEDBACK DISPROVED
- GetStatus requests returned structurally valid but non-changing position values.
- Therefore the radar cannot claim measured camera direction from those values.
- Preserve GetStatus as diagnostics, but mark unreliable position data correctly.
- Software direction tracking must be ESTIMATED unless independently verified.

PHASE 8: PHYSICAL STEP CALIBRATION
- User measurement established approximately 26 bounded clicks for 180 degrees of pan, approximately 52 clicks for 360 degrees, and approximately 6.923 degrees per click under the tested speed and pulse-duration profile.
- This is calibration evidence, not a universal constant.
- Default pan limits of -26 steps and +26 steps come from this measured half-turn model.
- Calibration must be tied to camera, axis, speed and pulse duration.

PHASE 9: BOOT-CALIBRATION MONITOR
- The camera's mechanical startup calibration was tested.
- Network and ONVIF service interruption were observable, but useful ONVIF position changes were not.
- Therefore startup mechanical calibration cannot be treated as an absolute software position source.

PHASE 10: READ-ONLY REQUEST MATRICES AND MAXIMUM ENUMERATION
- SOAP variants, endpoints, services, profiles, PTZ, Media, Media2, Imaging, Events, RTSP and selected ports were tested.
- Preserve proven protocol compatibility and response parsing.
- Treat these tools as diagnostic knowledge feeding the integrated Diagnostics tab, not as disconnected replacements for the main application.

PHASE 11: BOUNDED-PULSE MOVEMENT OWNERSHIP
- Safe movement was changed to finite ContinuousMove pulses followed by explicit Stop.
- Hard limits are checked before sending movement.
- Estimated counters change only after confirmed Move and Stop success.
- Stop failure causes UNSYNCED.
- Mouse hold, keyboard hold, focus loss, camera switching, Pause, Emergency Stop and clean shutdown must use this same movement-ownership model.

PHASE 12: REAL v1.5 OPERATIONAL PTZ MODEL
- This phase added pulse duration, pulse gap, Pan/Tilt speed, Zoom speed, step targets, per-camera limits, diagonal step planning, radar and calibration dependence.
- Preserve these operational concepts and integrate them into the complete application.

PHASE 13: VIDEO REINTRODUCTION
- Video was initially optional if direction could be known reliably.
- Once firmware position feedback proved unreliable and simulated behavior had masked missing functions, selected-camera video became an independent physical verification channel.
- Video must not be the camera-selection mechanism, but it must be available to verify real orientation and movement.

PHASE 14: FULL v2.0 INTEGRATION
- This phase attempted to recombine the broad v1 feature set with real/video improvements.
- Preserve the integration goal and video capabilities.
- Audit carefully for accidental restoration of old mock or backend behavior.

PHASE 15: UNIFIED v2.1 USABILITY
- The one-page UI had become too crowded.
- Task-oriented tabs were introduced to make the complete feature set usable.
- Preserve the tabbed organization even if specific v2.1 internals require correction.

PHASE 16: LATER DASHBOARD REGRESSION
- A later dashboard build used an older one-page source as its base and added radar/video visually.
- It looked like v1+, but lost tab navigation and later usability/functionality improvements.
- Do not use this build as the sole base.
- Preserve useful radar/video layout ideas only after reintegrating them into the complete tabbed application.

Do not begin the final merge until this lineage report is complete enough to explain why every major retained subsystem exists.

7. FINAL PRODUCTION FEATURE SET
================================================================

A. GLOBAL SHELL
- Professional Windows Tkinter/ttk interface.
- Task-oriented tabs.
- Active Camera block always visible outside tabs.
- Global connection status always visible.
- Global Emergency Stop always visible.
- Main status bar always visible.
- Beginner and Advanced views without data loss.
- Responsive resizing, scrollable/adjustable panels and no clipped controls.

Required tabs:
1. DASHBOARD
2. LIVE VIEW
3. PTZ CONTROL
4. PATROL & AUTOMATION
5. DISCOVERY
6. CAMERA SETUP
7. DIAGNOSTICS
8. LOGS & REPORTS
9. SETTINGS
10. optional ADVANCED TOOLS for real production diagnostics only

B. ACTIVE CAMERA SELECTION
- Double-click must not be required.
- Single-click selection or a clear Activate Camera button.
- Global camera selector.
- Active row/card highlighting.
- Display camera name, stable ID, host, ONVIF port, connection state, video state and PTZ command target immediately.
- Selection must be visible before video loads.
- PTZ, radar, patrol editor, calibration and video must always target the same selected camera.
- No selected camera means movement controls are disabled.
- Switching camera stops held movement and releases the old video decoder.

C. REAL PTZ CONTROL
- Up, Down, Left, Right and safe diagonals.
- STOP, Home, Zoom In, Zoom Out and Zoom Stop.
- Mouse-hold and keyboard-hold operation.
- Finite ContinuousMove pulses.
- Explicit Stop after every pulse.
- Per-camera Pan, Tilt and Zoom speed.
- Pulse duration in ms.
- Pulse gap in ms.
- Slow, Normal, Fast and Custom profiles.
- Hard-limit check before network transmission.
- Estimated counters update only after confirmed Move and Stop.
- Stop failure causes UNSYNCED.
- Focus loss, Pause, camera switching, Emergency Stop and shutdown use the same safe stop path.
- Unsupported controls are disabled from real capability results.
- Command feedback must distinguish NOT SENT, SENT, ACCEPTED, COMPLETED, REJECTED, TIMEOUT and FAILED.

D. RADAR, LIMITS AND CALIBRATION
- Camera-specific Pan and Tilt integer step tracking.
- Default Pan limit: -26 steps to +26 steps.
- Default Tilt range may begin at -26 steps to +26 steps but must remain independently configurable and must not be claimed as physically verified without calibration.
- Display remaining steps in each direction.
- Reliability state: MEASURED, CALIBRATED_ESTIMATE, ESTIMATED or UNSYNCED.
- Radar top represents display forward / 0 direction by default.
- Display forward and mechanical/calibration zero are separate settings.
- Do not let one overwrite the other automatically.
- Provide Set current as calibration zero, Set current as display forward, Reset estimate, Calibrate limits, Mark UNSYNCED and Resync actions.
- Calibration profile includes camera ID, axis, speed, pulse duration and date.
- Speed or pulse-duration change invalidates the matching calibration.
- Pulse-gap-only change does not automatically invalidate calibration.
- Never label software estimates as measured ONVIF coordinates.

E. PATROL AND AUTOMATION
- Independent patrol process per enabled camera.
- Stable EXEC values such as 10, 20, 30 and 40.
- Execution follows EXEC, not visual row position alone.
- Operations: GOTO_PRESET, WAIT, STEP_MOVE, bounded CONTINUOUS_MOVE, STOP, GOTO_HOME, verified ABSOLUTE_MOVE, verified RELATIVE_MOVE, SNAPSHOT and READ POSITION / SAVE VIEW.
- Step fields: enabled, EXEC, action, target, Pan steps, Tilt steps, Zoom, move timeout, settle time, dwell time, pulse duration, pulse gap, Pan speed, Tilt speed, Zoom speed and value source.
- Value source: EXPLICIT, CAMERA_DEFAULT, APPLICATION_DEFAULT or AUTOMATICALLY_INSERTED.
- Warn when movement steps have no meaningful observation dwell.
- Provide Insert Recommended Wait.
- Support Add, Edit, Delete, Reorder, Save, Load and Test One Cycle.
- Support ONCE, FIXED_COUNT, FOREVER and PING_PONG.
- PING_PONG must not duplicate endpoints consecutively.
- Preserve office-fan templates: TWO_POSITION_FAN, THREE_POSITION_FAN, FOUR_POSITION_SCAN, MAIN_WITH_BLIND_SPOTS, SLOW_PAN_LEFT_RIGHT, CAMERA_PRESET_TOUR and CUSTOM.

F. VIDEO
- Default to one selected-camera live stream.
- Camera selection must not depend on video startup.
- Preserve aspect ratio with black letterbox.
- Correct dynamic resizing.
- Latest-frame-only buffering.
- Clean decoder release on switch and shutdown.
- Snapshot, reconnect and optional fullscreen.
- Display masked URI, backend, resolution in px, frame rate in frame/s, codec, bitrate, latency in ms, dropped frames, reconnect count and last frame time when available.
- URI priority: configured URI, ONVIF Media1, ONVIF Media2, verified limited compatibility candidates, user-supplied URI, then truthful VIDEO ERROR.
- Backend priority: FFmpeg, OpenCV, VLC/libVLC, snapshot fallback, status-only fallback.
- Video failure must not stop patrol.
- Patrol failure must not freeze video.
- Multiview is optional and must create tiles only for real configured cameras.

G. CAMERA SETUP
- Add, edit, delete, enable and disable cameras.
- Name, stable ID, host, ONVIF port, RTSP port, protocol, profile token, PTZ configuration token, main/sub stream URI, snapshot URI and per-camera tuning.
- Atomic config save and backup.
- Preserve comments and ordering where possible.
- Remove outdated demo-camera defaults from production configuration.
- Do not hard-code the known camera as a universal assumption.

H. DISCOVERY
- Windows IPv4 adapters.
- User-approved local subnets.
- WS-Discovery, EndpointReference, Types, Scopes and XAddr.
- ARP and MAC support.
- Ping only as secondary evidence.
- QUICK, STANDARD and confirmed EXTENDED modes.
- Cancellation, concurrency limit and rate limit.
- Stable device identity and deduplication.
- Read-only ONVIF validation.
- User approval before adding or changing config.
- No brute force, password lists, public-internet scanning, unrestricted port scan, firmware change, reboot, reset, user creation, router modification or firewall modification.

I. DIAGNOSTICS
- Integrate knowledge from deep test, boot monitor, request matrix, forceful read-only and maximum enumerator.
- Environment, startup, discovery, per-camera capability, PTZ, Media, video and patrol reports.
- GetDeviceInformation, GetServices, Media1, Media2, GetProfiles, GetStreamUri, PTZ nodes/configurations/options, GetStatus, GetPresets, coordinate spaces and movement capabilities.
- Credential redaction everywhere.
- Every error must state what failed, likely cause, affected feature, whether operation can continue safely, corrective action, config key and report to inspect.

J. PRESETS AND SAVED VIEWS
- READ POSITION / SAVE VIEW workflow.
- Use capability tiers:
  1. real GetStatus plus verified AbsoluteMove;
  2. camera SetPreset/GotoPreset;
  3. RelativeMove for adjustment only;
  4. ContinuousMove as ESTIMATED only;
  5. disabled with explanation when no safe method exists.
- Saved view fields include ID, name, source, profile token, preset token, Pan, Tilt, Zoom, coordinate-space URI, timestamps, reliability, notes and optional snapshot.
- Do not move coordinates between incompatible cameras/spaces.

K. THREADING AND SAFETY
- One CameraWorker per camera.
- Commands serialized per camera.
- Different cameras may operate concurrently.
- GUI thread performs no network calls, blocking BAT calls or video decoding.
- Use thread-safe queues and root.after() UI updates.
- All waits are interruptible.
- Emergency Stop has highest priority.
- Cleanly stop workers, decoders and subprocesses.
- Required states include DISCONNECTED, CONNECTING, IDLE, MOVING, SETTLING, DWELLING, PAUSED, MANUAL_OVERRIDE, RECOVERING, STOPPING, ERROR and UNSYNCED.
